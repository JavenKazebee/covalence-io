# Milestone 7: Surfaces from plugins

- **Status:** Done, except the checks on hardware (Phase 7): a real MK.2, and the budgets on the Apple M3

A real Stream Deck drives Covalence, through a plugin. The core gets a device layer: it enumerates HID and serial devices, watches hotplug, matches them to plugins' manifests and performs their I/O, so a plugin of plain TypeScript can drive hardware with no native add-ons ([plugin protocol §13.6](../specs/plugin-protocol.md#136-device-drivers-are-plugins-the-core-performs-hardware-io)). The plugin host carries the surface protocol ([plugin protocol §8](../specs/plugin-protocol.md)), and `io.covalence.streamdeck` translates between the deck's reports and M5's surface model. Network transports arrive too, and the Videohub plugin moves onto them. MIDI, Orbitals and controls beyond keys stay out.

## Done when

- [ ] Plugging in a Stream Deck MK.2 (15 keys) is noticed by the core, matched to the Stream Deck plugin's `devices`, and gets a connection and a surface without asking (`autoCreate`). The surface shows its start layer, and its keys fire event triggers on `{layer, controls}` ([M6](m6-primitives.md)).
- [ ] Unplugging it detaches the surface and releases held keys. Plugging the same deck back in reattaches the same surface entity, matched by `model` and `serial`, showing the layer it showed last.
- [ ] `why` on an action fired from the deck walks back through `trigger.matched` and the key's `event` entry to the `state.patch` on `surface.<slug>.controls.k0.pressed`, with the host's `deviceTs`.
- [x] The Stream Deck plugin is TypeScript on `@elgato-stream-deck/core` with a backend over `ctx.hid`. No native add-ons, and no device-specific code in the core.
- [ ] Restarting the plugin host doesn't close the deck. The surface detaches and reattaches within 3 s, and the keys keep their last images meanwhile.
- [ ] Budgets hold with the plugin host in the path, measured from the device layer: key down → first action dispatched in under 5 ms, and state change → key image written to the device in under 16 ms.
- [x] A serial device (an ESP32 over USB CDC, or a fake one in tests) can be picked in a connection's form and read and written through `ctx.serial`.
- [x] The Videohub plugin uses `ctx.tcp`, and a connection's traffic can be viewed in the UI. A plugin with `directNetwork: true` is marked as not inspectable.
- [x] A Rust end-to-end test covers the above in CI against a fake HID Stream Deck and a fake serial device, with no hardware.

The unchecked items pass against the simulated MK.2 (Phase 7) and wait for the hand check with a real one; the budgets wait for a measurement on the hardware M5 used.

## Phases

### Phase 0: Decisions and docs
- [x] **[plugin protocol §13.6](../specs/plugin-protocol.md#136-device-drivers-are-plugins-the-core-performs-hardware-io):** device drivers are plugins; the core performs hardware I/O; network I/O is the plugin's choice. Protocol shapes in [plugin protocol §4, §7, §7.1 and §8](../specs/plugin-protocol.md), and `provider` and serial matching in [surfaces §1](../specs/surfaces.md).
- [x] **Spike: `@elgato-stream-deck/core` under Deno.** Passed with 7.9.0: it loads as `npm:@elgato-stream-deck/core`, its only dependencies are `tslib` and `eventemitter3`, and nothing in the tree is native. Its `HIDDevice` (`sendReports`, `sendFeatureReport`, `getFeatureReport`, `input` events) maps onto `ctx.hid`'s output, feature and input reports one for one. Over a stub, an MK.2 input report became `down 3` / `up 3`, and `fillKeyBuffer` wrote 1024-byte image reports.
  - **Images are the core's to encode.** The MK.2 takes JPEG, and the library calls an `encodeJPEG` the caller provides. In JS (`jpeg-js`) that's 146 ms for 15 keys warm, far over budget. Instead the core renders each key in the output's native format, and the plugin's `encodeJPEG` hands back the JPEG it was sent: 0.9 ms for 15 keys, with the bytes reaching the device unchanged. So the renderer gains `jpeg` (`jpeg-encoder`, pure Rust), and the plugin declares its image outputs as `{format: "jpeg", w: 72, h: 72, rotation: 180}`: gen-2 decks flip both axes, which the library skips when it doesn't encode.
- [x] **Choose the Rust crates.** All build with no system libraries, which matters for CI and a Raspberry Pi:
  - HID: `hidapi` with `linux-native-basic-udev` on Linux (hidraw, udev parsed in Rust; the default `linux-native` needs `libudev` headers), and the OS's own HID on macOS and Windows.
  - Serial: `serialport`, without default features.
  - Hotplug: `nusb::watch_devices()` for USB arrivals and departures on all three platforms, each one re-enumerating HID and serial; plus a once-a-second enumeration, for what isn't USB and in case a notification is missed.
  - JPEG: `jpeg-encoder`, for the renderer.
- [x] **Protocol schema:** `protocol/src/io.tsp` (`io.open`, `io.write`, `io.data`, `io.feature`, `io.state`, `io.close`, `device.list`, `DeviceMatch`, `DeviceInfo`) and `protocol/src/surface.tsp` (§8's messages and `ControlDef`), the manifest's `devices` and `directNetwork`, the Rust types in `covalence-protocol` (`io`, `surface`) with a `core_to_host` notification table, the TS method tables, and a fixture for each message, both sides' frames regenerated. `conn` is the envelope's, as for every connection's method. Bytes are a `Bytes` type: `bin` in MessagePack, an array of byte values in JSON, as both sides already wrote binary in the debug format. The core answers the new requests `unknown_method` and drops the new notifications, with a log line, until Phases 1–3. Phase 3 moves `covalence_core::surface`'s attach, input and control types onto the protocol's.
- [x] [plugin protocol spec §13.6](../specs/plugin-protocol.md#136-device-drivers-are-plugins-the-core-performs-hardware-io) settled: the spike passed.

### Phase 1: The core's device layer
- [x] **`covalence-devices`:** enumerate HID and serial devices, watch hotplug, and give each a stable `DeviceInfo.id` (§7.1). IDs are `hid:0fd9:0080:<serial>`, or `<kind>@<path>` without a serial number; interfaces of one device that share a serial gain `/<usage page>.<usage>`. Enumeration runs at once, on every USB arrival or departure (`nusb`), again 300 ms after it (HID and serial nodes lag the USB event), and every second. `cargo run -p covalence-devices --example devices` lists what the core sees, for checking hardware by hand.
- [x] **Matching:** installed plugins' `devices` against present devices; offers for unclaimed matches, and connections for `autoCreate`. A connection holds a device when its config names it (the first top-level string field with `format: "device"`) or it has a handle to it. A device is created without asking only when exactly one matching plugin says `autoCreate`; otherwise it's offered once, with every matching plugin to choose from. Automatic connections are `live`, aliased after the plugin ID's last part (`deck`, `deck2`). `GET /devices` lists each device with `heldBy`, its handle and its `offer`. The SDK passes `devices` and `directNetwork` through to the manifest.
- [x] **Handles:** one connection per device (`busy`), unplug and replug as `io.state`, and handles kept open across a plugin host restart. A device that isn't plugged in, or that the OS refuses, still gets a handle whose first state says why; it opens when the device is plugged in (again). Each open device has an I/O thread that owns its port: writes go out in order, between reads of at most 2 ms. `detach` drops a holder's input while keeping the device open, and the holder's next `open` gets the same handle back.
- [x] **A fake backend** for tests: plug, unplug, input reports in, output and feature reports recorded (`covalence_devices::fake`, with an MK.2 and an ESP32 to plug in). The server takes it through `Config.devices`.
- [x] OS errors that the UI can explain (§7.1): `permission_denied`, `exclusive_access`, `no_driver` and `unplugged`, each with a hint for the platform (udev rules, Input Monitoring, another app holding the device, WinUSB).

### Phase 2: Transports in the protocol and the SDK
- [x] `io.open`, `io.write`, `io.data`, `io.feature`, `io.state` and `io.close` for `hid`, `serial` and `tcp`, and `device.list`. They're `covalence_core::io`'s, which the host supervisor owns: it sends a host's `io.data` and `io.state` while the host is up, keeps device handles open (input dropped) when it goes, and closes sockets. `io.open` of `tcp` answers after the first attempt to connect, failing with `not_connected` unless `reconnect` is set; `line` framing keeps each line's `\n`, and `length` reads a 4-byte big-endian length before each message. Requests run off the session loop, and a connection can use only its own handles. `busy` joins the protocol's error codes (it was in §9 but not in the schema).
- [x] SDK: `ctx.hid`, `ctx.serial` and `ctx.tcp`, with `ctx.tcp` shaped like `Deno.Conn` and `ctx.net.socket()` like a `node:net` `Socket`. The device config format and its picker. Also `ctx.devices.list()`. Workers send requests to the core through the host, and the host passes `io.data` and `io.state` to the connection's worker. A destroyed connection closes its handles. The connection form offers a `format: "device"` field's matching, unheld devices (`GET /devices?plugin=`).
- [x] A connection's traffic is kept in a ring buffer per handle and served at `GET /connections/{id}/traffic`: the last 500 messages of each handle, up to 512 bytes of each in hex, with state changes, and the last 8 closed handles per connection. It says whether the connection is `inspectable` (not `directNetwork`).

### Phase 3: Surfaces over the plugin host
- [x] The core accepts §8 notifications from the plugin host, with `conn` as the provider, through the transport-independent surface module M5 built. Images go as binary frames. The host supervisor hands them to the server (`PluginSurfaces`), which attaches them as the web surface does and sends each draw back as `surface.draw` with the connection's own key for the surface. The protocol's control and input types are converted to the core's at that edge, rather than replacing them: the core's are stricter and the web surface speaks them. The renderer gains `jpeg` (`jpeg-encoder`, quality 90) and `rotation` (0, 90, 180, 270), and an attach whose image outputs it can't draw is refused.
- [x] Surface entities are created on first attach and matched by `model` and `serial` after that; `provider` is set. A surface without a serial is matched by `model` and provider. When another connection attaches the same device, `provider` follows it.
- [x] A connection that stops (deleted, disabled, host lost) detaches its surfaces, releasing input as on any detach (surfaces §4.1). Deleted and host lost are covered; there's no disabling yet.
- [x] SDK: `ctx.surfaces.attach(...)` with the button presets, giving input to send and draws to receive: `down`, `up`, `turn`, `value` and `touch` with the device's `ts`, and `onDraw`. Presets: `button`, `encoder`, `fader`, `touchstrip`, `lcd`, `led`, `keys(cols, rows, image)` and `row`. A destroyed connection detaches its surfaces.

### Phase 4: The Stream Deck plugin
- [x] `plugins/streamdeck`: `devices` for Elgato's vendor ID and the MK.2's product IDs, `autoCreate: true`. It's a first-party plugin the server loads by default. Its `devices` list every keys-only model in `@elgato-stream-deck/core`'s table, not just the MK.2's. Its one action sets the brightness, and its state has the model, serial number and firmware.
- [x] Attaches 15 `momentary` + `image` controls placed with `at`, in the device's native image size, format and rotation; turns key reports into `surface.input` with the report's time as `ts`; writes `surface.draw` images to the device. `io.data` gains `ts`, when the core read the report, which becomes the press's `deviceTs` in the journal. The format and rotation come from a probe at open: the library prepares (without sending) an image whose pixels hold their own coordinates, and where they land in `encodeJPEG` gives the core's turn. The MK.2 comes out at JPEG turned 180°, as the spike found. The core's JPEG then goes out through `encodeJPEG` unchanged. Unplugged, the surface detaches; plugged back in, it attaches again and is redrawn.
- [x] Other models the library supports work if they only have keys, but only the MK.2 is checked by hand. Gen-1 models, which the library packs as BMP itself, are sent raw RGB: `rgb` joins the protocol's image formats and the renderer's.
- [x] A protocol-level simulator of the MK.2 for tests: `covalence_devices::fake::Mk2` answers the serial number and firmware feature reports, sends 512-byte key reports, and reassembles the JPEG of each key from its image reports. The UI's virtual deck is unchanged. The test plugin moved to pid.codes' test vendor ID, so it no longer competes with this plugin for MK.2s.

### Phase 5: Network transports and the Videohub plugin
- [x] The Videohub plugin moves from `Deno.connect` to `ctx.tcp`, with reconnects from the core. It opens one socket with `reconnect` and `line` framing, so the inspector shows the protocol a line at a time; the socket's `open` resets the prelude and `reconnecting` becomes `disconnected` (or `error` before the first prelude). A link that sends no prelude is closed and a fresh socket opened, with the plugin's own backoff. `TcpConn.onState` now keeps its place among the bytes: a change fires once the bytes before it have been read, and one that arrives before anything listens (the first `open` can beat `connect`'s answer) waits for the next `read`. `@covalence-io/sdk/testing` has `LocalTcp`, the core's `tcp` transport over Deno sockets, for testing plugins live without the core; the plugin's tests and the host's `FakeCore` use it. `crates/covalence-server/tests/videohub.rs` runs the plugin live through the real core against a fake Videohub: routes, the traffic view and a reconnect on the same handle.
- [x] `directNetwork` in the manifest, shown on the connection: `GET /connections` says `directNetwork: true` for a connection whose plugin declares it (read from the manifest, not stored), and the connections list marks it "direct network". Its traffic is `inspectable: false`, as in Phase 2.

### Phase 6: UI
- [x] Found devices: what's plugged in, which plugin and connection hold each, and offers for unclaimed matches. A Devices panel on the Connections screen lists `GET /devices`, looking again every 2 s since hotplug isn't on the WebSocket: each device's name, kind and USB IDs; the connection that holds it, its handle's state and whether a surface is attached on it; or, for one no connection holds, "Set up with …" for each plugin that matches it, which fills the new connection form (the plugin, live mode, an alias made as the server makes them for `autoCreate`, and the device in the config's `format: "device"` field). A device being given a connection by `autoCreate` says so.
- [x] A connection's traffic view, and the "not inspectable" mark for `directNetwork`. `#/connections/<alias>`, linked from each connection's row and from the device it holds, shows `GET /connections/{id}/traffic` a handle at a time, newest first, polled every second unless paused: time, direction, length (and whether the 512 bytes kept were cut), and the bytes as text when they're mostly printable, as the Videohub's lines are, or as hex. A connection whose plugin declares `directNetwork` says it isn't inspectable, and why.
- [x] A surface shows its provider, and whether it's attached. The surfaces list has a Provider column (the connection, linked to its traffic, or "This browser" for a virtual deck). A plugin's surface no longer gets a virtual deck on its page: it shows whether it's attached, its provider, model and serial, and the layers that fit the controls it last attached with.

### Phase 7: Acceptance
- [x] The Rust end-to-end tests against fake devices run in CI, in the existing `cargo test --workspace --locked` job with Deno. Against the simulated MK.2 and the real plugin, `streamdeck.rs`'s `a_stream_deck_runs_flows_and_rides_out_unplugs_and_host_restarts` covers what "done when" asks of the deck: a surface made ahead of time with its model, serial and a start layer is the one the deck attaches as, showing that layer; a key on it runs a flow whose action reaches the deck, and `why` on that action ends `trigger.matched`, `event`, `state.patch` on `surface.<slug>.controls.k0.pressed` with `deviceTs`; unplugging with a key held releases it, and replugging in another port reattaches the same surface showing the same layer; killing the plugin host leaves the deck open (one open), the surface back within 3 s, nothing reset, and every key redrawn with the image it had. `devices.rs`'s `a_serial_device_picked_for_a_connection_is_read_and_written` picks an ESP32 from a plugin's device list, opens it at the plugin's baud, reads and writes it through `ctx.serial`, sees its traffic and follows an unplug. The fake device log now records when each write and feature report arrived, for timing.
- [ ] Checked by hand with a real MK.2: plug in, press a key that routes the Videohub, see the bound key redraw, unplug and replug, restart the plugin host.
- [ ] Budgets measured with the plugin host in the path, including the round trip M5 left unmeasured. **Measured against the simulated MK.2; still to measure on the hardware M5 used.** `streamdeck.rs`'s `bench_budgets_with_the_plugin_host_in_the_path` (ignored; run in release) times both paths where the core's device layer meets the device. On a 4-core cloud container, in release, with M5's core-only bench run on the same machine for scale:

  | Path | Budget | Core only (M5's bench, same machine) | With the plugin host and the MK.2's reports |
  |---|---|---|---|
  | State change → 15 keys at 72 px JPEG written, 2 `expr` bindings each | 16 ms | 19.7 ms (M3: 9.0 ms) | 29 ms median, 38–46 ms worst; first key at 24 ms |
  | Key down → action | 5 ms to dispatch | 0.23 ms to dispatch (M3: 24.5 µs) | 5.0–5.2 ms median to the action's feature report at the deck, through the plugin both ways |

  This machine is about 2.2× slower than the M3, and over the redraw budget without a plugin. The plugin adds about 5 ms before the first key reaches the deck and about 5 ms to stream the other 14, which scales to roughly 13–14 ms in all on the M3: inside 16 ms, without much room. Key down to the action at the device crosses the plugin host twice, so dispatch, which crosses it once, is about half of it. Both need confirming on the M3 with the real deck, which also adds USB time the fake doesn't have.
- [x] Carried forward from M5: what a surface shows is kept across a server restart, so a surface without a start layer comes back showing the layer it showed last. The core's `Surfaces` says when what a surface shows changes (`on_shown`), the server stores it as a `surface_shown` entity, and loads it back at startup (`restore_shown`), which also publishes `current.main` before the surface attaches. `surfaces_api.rs`'s restart test checks a surface moved off its start layer and one with none, before and after attaching. That test now keeps the old app's surface link until it ends: dropping it journaled a detach from the stopped app, racing the restarted one's first write to the same database.

## Ordering

Phase 0 comes first. Phases 1 and 2 can run side by side once the protocol shapes are in TypeSpec. Phase 3 needs Phase 2's transport. Phase 4 needs Phases 1–3, but can start against the fake backend after the spike. Phase 5 needs only Phase 2's `ctx.tcp`. Phase 6 follows the APIs it shows, and Phase 7 joins them.

## Out of scope

MIDI and `ctx.midi` · `usb`, BLE and GPIO · Stream Deck models with dials, touch strips or LEDs, and `led`, `level` and `text` outputs and brightness · Orbitals and routing traffic through them · `ctx.udp`, `ctx.ws` and `ctx.http` · record/replay of traffic · permission enforcement ([plugin protocol §13.5](../specs/plugin-protocol.md#135-permissions-are-declared-now-enforced-later)) · native add-ons and helper processes for vendor SDKs · a WASM plugin host · plugin-provided pure functions, interfaces and time sources · surface groups · everything left out of M5.
